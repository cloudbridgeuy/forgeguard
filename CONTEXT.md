## Glossary

### Resolution engine vocabulary

| Term | Definition |
| --- | --- |
| **Resolution engine** | ForgeGuard's central function: turn `(HTTP request, customer config)` into a Cedar `IsAuthorized` request. Pure — does not call VP or any decision backend. The boundary between the engine and the decision layer is what makes Cedar / VP / mock evaluators swappable behind ForgeGuard. _Avoid_: "authz engine," "auth engine" (both imply decision-making). |
| **Cedar request** | The resolution engine's output: a `(principal, action, resource, context, entities)` value object ready for any Cedar evaluator. _Avoid_: "authz query." |
| **Decision layer** | The I/O wrapper that takes a Cedar request, queries a backend (Verified Permissions, Cedar-as-library, mock), and returns Allow/Deny + diagnostics. Lives in I/O crates; swappable per deployment. _Avoid_: "authz client." |
| **Extractor** | The customer-authored primitive that produces a value for one slot from one source. Two kinds: **pure extractor** (I/O-free — request headers, JWT claims, path params, static literals) and **effectful extractor** (I/O-bound — DDB lookups, callbacks, remote APIs). The pure/effectful split predicts which extractors are usable in which enforcement strategy (pure work everywhere; effectful require host capabilities). _Avoid_: "resolver," "binding." |
| **Source** | Where an extractor reads from. ForgeGuard ships the catalogue (`jwt_claim`, `header`, `cookie`, `path_param`, `host`, `body_field`, `static`, `callback`, `dynamodb_membership`, `system_clock`, …); customers compose extractors from this catalogue. The catalogue evolves with releases; customers do not add new sources (except via the `callback` source in axum/core). _Avoid_: "provider," "reader." |
| **Slot** | A Cedar attribute the engine must populate. Four families: (1) **Principal** — `principal.id`, `principal.parents`, `principal.{attr}`; fed by the **Principal chain** (global or route-scoped override). (2) **Resource** — `resource.id` (route-scoped extractor; required for instance actions, forbidden for collection actions), `resource.parents`, `resource.{attr}` (app-supplied inline on the `IsAuthorized` call). (3) **Context** — `context.{key}`; route-scoped extractors fed by the Source catalogue; populated only when an applicable policy references the key. (4) **Action** — derived from the matched route, never extracted. An extractor *targets* a slot. _Avoid_: "target" (used as field name only), "field." |
| **Required-slot manifest** | The set of slots an action requires, computed per-action. Output of static analysis on raw Cedar policies, or emitted by-construction by DSL-pattern compilation. The engine validates at config-load that every manifest slot has a declared extractor; missing extractors are a config error, not a runtime failure. Manifest also enforces **Action scope** invariants: declaring `resource_id` on a collection-scoped action is a hard error; declaring `resource_id` on an instance-scoped action whose policies don't reference `resource.id` is dead config (warn in dev, hard error in strict mode). _Avoid_: "required attributes," "schema needs." |
| **Authoring layers** | The two-layer model for policy authoring. **Layer 1: raw Cedar** — lowest abstraction; the customer writes Cedar `permit`/`forbid` directly (inline in `forgeguard.toml` as triple-quoted strings, or in separate `.cedar` files referenced from the TOML), and ForgeGuard derives the required-slot manifest via static analysis. **Layer 2: DSL patterns** — higher-level compilers (today: RBAC; future: multi-tenant sugar, ABAC sugar, sharing-grant sugar) that emit Cedar + manifest by construction. Both layers feed the same `(policies, manifest)` contract into the engine. **Mixing semantics:** when both layers are present, the engine takes the union of policies and the union of manifest slots. If both layers reference the same slot with different types (e.g., L1 expects `tenant_id: String`, L2 expects `tenant_id: Long`), that is a config-load error. _Avoid_: "frontend/backend," "DSL/engine." |
| **DSL pattern** | A specific Layer-2 compiler. Each pattern owns its grammar in `forgeguard.toml`, its compilation to Cedar, and its required-slot emission. Patterns can be **generators** (pure compilers that produce policies + manifest from their own TOML section; today: RBAC, future: ABAC, sharing-grant) or **transformers** (rewrite the merged Layer-2 policy set; today: Tenancy sugar). Composition is a two-phase pipeline — all generators run first (in any order; their outputs are independent), then transformers run in a fixed order shipped by ForgeGuard, then Layer 1 raw Cedar policies are merged in (transformers do not touch Layer 1). Adding a generator is additive; adding a transformer is a higher-review change that locks its position in the order. The catalogue is closed — customer-authored patterns are deferred (the documented extension path is raw Cedar at Layer 1). _Avoid_: "macro," "preset." |
| **Tenancy sugar** | The DSL pattern that opts a project into multi-tenancy. The customer declares `[tenant]` with a source; ForgeGuard auto-creates the principal-side extractor, defaults `resource.tenant_id` to inherit from `principal.tenant_id`, auto-appends `when { principal.tenant_id == resource.tenant_id }` to **Layer 2-compiled policies only** (raw Cedar in Layer 1 is left untouched — predictability over implicit safety), and supports per-resource-type override (`tenant_source = ...` for OwnId-style scenarios) and opt-out (`tenant_scope = "global"`). The manifest check warns at config-load when a Layer 1 raw policy in a tenant-scoped project does not reference the tenant clause and is not marked `cross_tenant_acknowledged = true`; strict mode promotes this to an error. Without `[tenant]`, ForgeGuard imposes no tenancy. _Avoid_: "multi-tenant mode," "tenant scoping" (used as the per-resource-type knob only). |
| **Mandatory extractor set** | The minimum extractor declarations every customer must supply: **Principal** (id + entity type) via the **Principal chain**. Route declarations supply the action and resource entity type. For instance-scoped actions, a **Resource id** extractor is also required (route-scoped, via `resource_id`). For collection-scoped actions, the engine synthesizes the resource — no `resource.id` extractor needed; the route may declare `context.<name>` extractors for policy-referenced inputs (e.g., parent folder id). ForgeGuard ships default context extractors (`now`, `client_ip`, `request_id`) which the customer can override but cannot disable. Everything else is policy-driven via the required-slot manifest. |
| **Principal chain** | The ordered, first-success-wins sequence of principal sources. Two-tier: a **global chain** (`[[principal_sources]]`) lists sources that can apply to any route (e.g., `jwt_claim`, `ed25519_signature`); a **route-scoped override** (`[[routes]].principal_source`) replaces the chain for that single route (used when the principal is tied to the route shape — e.g., `path_param` for magic links, share tokens, webhook callbacks). Sources have preconditions (path_param: param present on the route; jwt_claim: `Authorization` header present at runtime); chain skips sources whose preconditions fail. Manifest check rejects route-scoped sources whose preconditions cannot be satisfied by the route's declared shape (e.g., `path_param: token` on a route without `:token`). _Avoid_: "auth chain," "identity chain" (the latter is the internal proxy implementation name, not the customer-facing concept). |
| **Action scope** | A primitive distinguishing **collection-scoped** actions (operate on an entity type as a whole; no `resource.id` required; route may declare `context.*`) from **instance-scoped** actions (operate on a single instance; `resource.id` extractor required). Derivation rule from action name verb suffix: `list`, `search`, `index`, `create` → collection; everything else (`read`, `update`, `delete`, `share`, custom verbs) → instance. Per-action explicit override via `[[actions]].scope = "collection" \| "instance"`. HTTP-method conventions follow scope (`list` → `GET`, `create` → `POST`) but are observed, not enforced. |
| **Action name** | A single string that becomes the Cedar `Action::"<name>"` EID. Two conventions in active use: (1) **colon-separated** `namespace:entity:verb` — the canonical customer-facing format documented in `forgeguard.example.toml` (e.g., `todo:list:read`, `shopping:item:add`); (2) **hyphen-separated** `namespace-entity-verb` — used by the CP dogfood (`cp-proxy-config-read`, `cp-organization-delete`). Both encode `namespace + entity + verb`; the project does not impose one over the other. Action names are **not** Cedar entity types; do not write `Note::read` (that means entity type `Note`, EID `read` — wrong). The verb suffix drives **Action scope** derivation; the entity component drives the route → resource-type implicit binding. |
| **Engine invariants** | The product guarantees a customer cannot override: Cedar semantics, the `(principal, action, resource, context, entities)` request shape, static-analysis derivation of required slots, slot-completeness checking at config-load, default-deny on authn failure, Cedar `forbid` precedence, the auto-appended tenancy clause for DSL-compiled policies when Tenancy sugar is declared, and the ForgeGuard-controlled source catalogue. _Configurable_: authn provider (Cognito vs BYO IdP), decision backend (VP vs Cedar-as-library), per-route public access via `[[public_routes]]`. |
| **Cedar templates** | Parameterized policies with policy slots (`?principal`, `?resource`) filled at link time. They fit the two-layer model with no new primitives: customer-authored templates live in Layer 1 (inline or in `.cedar` files); DSL generators may also emit templates. **Manifest is derived from the template body**, not from runtime-linked instances. Linked policies live in VP and are created/destroyed via the data plane's link API; they do not widen the required-slot manifest because their slots were already counted on the template. _Avoid_: "parameterized policy" (ambiguous), "policy template" (acceptable but conflict with infra IaC templates). |
| **Schema derivation** | The Cedar schema is **derived by default** from the customer's `forgeguard.toml`. Algorithm: walk action declarations (and routes) for action names; walk policies (Layer 1 + Layer 2 emissions) and extractor declarations for entity types; walk attribute references in policies and infer types from extractor source declarations; compose and validate against Cedar's schema rules. Customers override per-attribute via `[schema.entity_types.X.attributes.Y]` or with a full hand-written `[schema] file = "..."`. Attribute referenced in a policy with no source/override declaring its type is a config-load error; derived/override conflict is a config-load error. _Avoid_: "schema inference" (used loosely; "derivation" is the precise term)._ |

### Domain model

| Term | Definition |
| --- | --- |
| **Tenant** | The most common scope primitive in ForgeGuard's exposed model, made available via the **Tenancy sugar** Layer-2 pattern. When opted in (via `[tenant]`), every protected resource of a tenant-scoped type belongs to exactly one Tenant; every Principal acts inside a Tenant; and the resolution engine populates `principal.tenant_id` and `resource.tenant_id` from declared extractors. Tenancy is **not** imposed on projects that don't declare `[tenant]` — ForgeGuard supports flat, resource-only authorization just as well. The wire-format attribute name is `tenant_id` by default and customer-configurable. The display name in any given UI is independent: ForgeGuard's CP renders its Tenants as "Organizations"; a customer's TODO app may render them as "Workspaces." The internal term is always `tenant`. |
| **Organization** | ForgeGuard's *display name* for the Tenants that live inside the CP-dogfood policy store. Each Organization is the billing/admin/IdP-wiring unit for one ForgeGuard customer. Implementation-wise it is just a Tenant with extra fields (billing metadata, Cognito user pool reference, VP policy-store reference). Identified by `OrganizationId`, which is the `tenant_id` value used in the CP-dogfood store. Customers do not see this name except in the ForgeGuard dashboard UI. |
| **Tenant naming layers** | ForgeGuard separates three concerns: (1) **internal vocab** — the codebase and docs always say `tenant`; (2) **wire format** — JWT claims and Cedar attributes are `tenant_id` by default, override per customer via `--tenant-claim-name`; (3) **display name** — every customer (including ForgeGuard's own CP) picks the label end-users see ("Organization," "Workspace," "Account"). Decoupling these means a customer whose JWTs already carry `workspace_id` does not have to rename anything, and a customer who calls their tenants "Accounts" in marketing can do so without touching the authz engine. |
| **ForgeGuard IdP (the product)** | ForgeGuard's primary product is an Identity Provider. Customers sign up, get a hosted login surface, and integrate their app via OIDC. ForgeGuard issues all access tokens for the customer's end-users. Cognito is the current implementation; customers never see it as Cognito — they see "ForgeGuard Auth." The CP dashboard dogfoods the same IdP product for its own admins. |
| **Proxy (escape hatch)** | The self-hostable proxy binary is a deployment option for customers who want enforcement to run in their own infrastructure (BYOC). It is *not* the primary product — most customers consume ForgeGuard as a managed authz API + hosted IdP. The proxy remains supported for regulatory/latency/data-residency cases where a SaaS gateway is not acceptable. |
| **Customer `forgeguard.toml`** | The canonical artifact a ForgeGuard customer authors to declare their entire AAA layer: action catalog, resource type schema, roles (RBAC), Cedar policies/templates (escape hatch), and any per-tenant overrides. Same shape as ForgeGuard's own `forgeguard.toml` (the CP-dogfood reference). Lives in the customer's git repo or is generated by the dashboard. The dashboard UI and Management API are both CRUD wrappers that produce/consume the same TOML — there is no second source of truth. Power users (and AI agents) author it directly; non-technical admins use the UI. |
| **Enforcement strategy** | How a customer plugs ForgeGuard into their app. Three supported shapes, all consuming the same compiled enforcement bundle from the CP: (1) **`proxy`** — sidecar/gateway binary, no app changes required; (2) **`forgeguard_axum`** — Axum middleware embedded in a Rust app; (3) **`forgeguard_core` / FFI bindings** — direct library use from Rust, Python (PyO3), or WASM. The customer's choice is operational, not architectural — ForgeGuard's exposed model and the customer's `forgeguard.toml` are identical regardless of which is chosen. |
| **AAA Layer** | ForgeGuard's product framing: it provides Authentication (the hosted IdP), Authorization (Cedar-backed policy engine + RBAC compiler), and is laying the groundwork for Auditing (CloudTrail-shaped, future). Modeled after AWS IAM's shape: Users hold Memberships in Organizations (tenants), which delegate permission to execute Actions on Resources via Cedar policies. ForgeGuard's CP dogfoods this model on its own admin surface — the CP is just another customer's app whose `forgeguard.toml` happens to ship with ForgeGuard. |
| **Control Plane** | ForgeGuard-operated SaaS: organization management, policy authoring, dashboard, billing. Contains no customer user data. |
| **Data Plane** | The runtime enforcement layer: proxy, identity resolution, authorization decisions. In SaaS mode, operated by ForgeGuard. In BYOC mode, deployed in the organization's AWS account. |
| **BYOC (Bring Your Own Cloud)** | Deployment model where the data plane runs in the organization's AWS account while the control plane remains ForgeGuard SaaS. |
| **Proxy (local — static)** | Single-organization proxy binary in static mode. Reads TOML config, fully self-contained. No control plane dependency. |
| **Proxy (local — connected)** | Single-organization proxy binary in connected mode. Fetches routes, flags, and upstream config from the control plane. Organization provides local AWS resource IDs (Cognito pool, VP store) at startup. The control plane syncs Cedar policies to the org's VP store. |
| **Proxy (SaaS)** | Multi-organization proxy binary operated by ForgeGuard. Resolves organization from request, lazy-loads per-org config via L1 in-memory cache, L2 CloudFront/S3 (SaaS) or authenticated Lambda API (BYOC). |
| **Worker** | Background Lambda binary (`forgeguard_worker`). Dispatches jobs by `FORGEGUARD_WORKER_JOB` env var. Currently: `reconciler` (sync pending DynamoDB records to S3). |
| **Promotion** | A control-plane record that an external resource (identified by an FGRN) has been promoted into an org's authorization graph. Store-level only — no create HTTP API; lifecycle managed via `DELETE .../promoted-resources/{resource_type}/{native_id}` (idempotent tombstone) and `GET .../promoted-resources` (reconciliation list). See [Control Plane](./.claude/context/control-plane.md). |
| **Membership** | A user's relationship to one organization, persisted as a DDB row keyed `PK=USER#{sub}, SK=ORG#{org_id}`. Carries the user's role/group set inside that org. |
| **Default organization** | The org a user lands in when no hint is supplied at token-mint time. Stored per-user in DDB. Optional — a user may have none. |
| **Active organization** | The org context for the current request. Carried by the JWT's `org_id` claim. Derived per-mint by PTG, never persisted as "current selection" state. |
| **Org-id hint** | A per-mint signal from the dashboard SPA — passed via Cognito `ClientMetadata.org_id_hint` on `InitiateAuth` — that PTG validates against memberships before injecting `org_id`. Priority: hint > default > bare. |
| **PTG (Pre Token Generation V2)** | Cognito Lambda trigger that customizes JWT claims at mint time. ForgeGuard's PTG queries DDB for memberships and the user's default org, then injects the `org_id` claim. |
| **Bare token** | A Cognito JWT minted without an `org_id` claim — the user has no hint, no default, or no valid memberships. Only `/api/v1/me` and `/api/v1/me/memberships` accept bare tokens. |
