# ForgeGuard — Candidate Engineering Design A1, and Its Feasibility Report

*Version 1.0 — July 2026*
*Status: one candidate engineering design, subordinate to the Problem & Product Brief v1.4. Unlike the brief, this document names technologies freely — that is its job. A competing design (different language, engine, or storage) that passes the same gates is equally conformant. This document ends with the report the design was commissioned to produce: feasibility, wins, shortcomings, cost studies with break-even numbers, and a wary list.*
*Evidence basis: a working evaluation spike was compiled and benchmarked during this design session (source in `forgeguard-spike-cedar.rs`), and the cost model was computed, not estimated by feel. Both are container-grade evidence — directionally strong, to be re-run on target hardware before the numbers are treated as production commitments.*

---

## Design overview

A1 is the design the founder's own skills reach fastest: a Rust workspace whose crates mirror the brief's planes, enforcing the Functional Core / Imperative Shell split at crate boundaries.

`fg-core` holds the pure model: FGRN types, the spine with its tree constraint and user-boundary rule, grant edges, delegation chains, the cardinality doctrine's promotion logic. No I/O. `fg-compiler` turns structural policy files plus operational-plane state into a versioned snapshot — concretely, a compiled Cedar `PolicySet` plus schema plus a provenance map — and runs the validation passes (mandatory deny fields, selector resolution against the spine). `fg-engine` wraps the embedded `cedar-policy` crate: it builds the entity slice for a decision from one consistent store read, evaluates, applies the delegation-chain intersection, and emits the decision record carrying snapshot version and grant revision. `fg-store` is the trait the brief's consistency section demands — snapshot-at-revision reads, revision-returning writes, a change stream — with the MVP implementation on PostgreSQL and the trait shaped so a Zanzibar-class backend can slot in later. `fg-log` owns the two append-only truths this crate family produces: the decision log and the per-Organization event log with its gap-free sequence. `fg-sync` exposes the cursor endpoint and, in a later phase, Standard-Webhooks-conformant push. `fg-middleware` is the first enforcement body — a Tower layer for Axum implementing the header contract (Ed25519 via a standard Rust signing crate), the per-endpoint enforce/observe switch, and the session-context bridge to RLS. `fg-proxy`, the Pingora body, is deliberately a later phase.

The engine choice deserves one paragraph of justification since Report 2 left it open: Cedar-as-a-crate is Class A (passes the footprint and latency gates by construction), its forbid-overrides-permit semantics are the brief's deny order natively, its entity-parent DAG expresses the spine and grants as one mechanism — and the spike below demonstrates that all five of the brief's killer behaviors, including the user-boundary opacity and chain intersection, compile to it without contortion. The known costs (selector compilation, entity slicing, chain logic living in the wrapper) are accepted and owned by `fg-compiler` and `fg-engine`.

Storage strategy is the design's quiet keystone. The MVP's grant store, event log, and decision buffer live in **the application's own PostgreSQL** — which is what makes the free tier's footprint gate pass *by definition*: ForgeGuard adds tables, not services. Two properties fall out almost free. First, **single-revision evaluation costs nearly nothing**: a decision's entity slice is read inside one MVCC snapshot (`REPEATABLE READ`), so the brief's never-mix-revisions rule is enforced by the database's own consistency model rather than by bespoke machinery. Second, the **gap-free per-Organization sequence** is a serialized counter update inside the same transaction as the mutation — trivially correct on one database, with a known contention ceiling analyzed in the wary list.

Deployments: the MVP is the middleware embedded in the founder's application on the homelab cluster, tables in that app's Postgres, decision log to stdout and object storage, cursor endpoint served by the same process. The hosted control plane (post-validation) is a small AWS deployment — container API in front of a modest RDS/Aurora instance, object storage with lifecycle rules for logs, Stripe for tenant-metered billing, and webhook push bought per Report 2's Class E (Svix-class, Standard Webhooks conformant, with the sequence and Organization-key signing living in payloads so the vendor is replaceable). The proxy body, the operational UI, and multi-region come only after the model survives the n=1 month.

## Key mechanisms against the brief's contracts

**Consistency.** Revision tokens are the Organization's event-log sequence number; every mutation returns one, every decision records one, and `X-Fg-Min-Revision` on a request forces a store read at least that fresh (on single-Postgres, a plain read after checking the counter — cheap). The deny hot channel is degenerate in the MVP — one process, one store, denies read strongly on every decision from a set that is almost always empty — so the ≤1s revocation SLO is met trivially; the *distributed* hot channel (proxy fleet, listen/notify or stream fan-out) is the proxy phase's headline engineering problem and is explicitly not solved by this document. Degraded-mode defaults, staleness flags in headers and decision records, and per-endpoint `consistency` declarations are implemented in `fg-middleware` per the brief.

**Synchronization.** The event log is an append-only table `(org, seq, event_id, kind, payload, signature)`; the cursor endpoint is a paginated read from it; replay is a `WHERE seq > $cursor`. Push is delivery over the same rows. The position dimension table, principal upserts (keyed by app-native id), and tombstones are exactly the brief's flows, implemented as thin handlers over the log and store.

**Data plane.** The middleware sets `fg.scope_path` and `fg.granted_ids` as Postgres session settings; ForgeGuard ships reference RLS policy templates per visibility mode. Because MVP middleware and app share the database, the dimension table is not even a sync in phase one — it is a view over ForgeGuard's own spine tables, deferring the replication machinery until a second body or external database exists.

## Variant A1.1 — serverless control plane (Lambda/Rust + DynamoDB)

The founder's original stack — Rust on Graviton Lambda, DynamoDB, EventBridge-style eventing — re-earns its place through the gates as a control-plane variant, with the customer runtime completely unchanged. Fixed platform cost collapses from $130–380 to **$17/month lean, ~$117 comfortable** (API Gateway + Lambda + DynamoDB on-demand scale to zero); marginal costs drop to **$0.22 per entry Organization (99% margin)** and **≈$33 per B2B Organization (93% margin)**; infrastructure break-even becomes **one customer of either tier**. Operationally it is the correct shape for a team of one: nothing to patch, nothing idling, and the founder's deepest AWS fluency.

The trade is architectural and chosen with eyes open. The gap-free sequence survives cleanly as a `TransactWriteItems` pairing a conditional counter increment with the event write — the same per-Organization serialization ceiling, with throttle-and-retry replacing lock waits. What does not survive is MVCC: DynamoDB offers no cross-item snapshot reads beyond a 100-item serializable `TransactGetItems` at double cost. This matters less than it first appears, because A1's hot path never touched the control-plane database — runtime evaluation is customer-side — and it pushes the variant somewhere genuinely cleaner: **event sourcing as the control plane's native shape**. With the event log as source of truth, state at revision N is a fold over events up to N; snapshot compilation reads a log prefix; single-revision consistency becomes a property of a log position rather than a database isolation level — arguably a purer realization of the brief's sources-are-truth, snapshots-are-derived doctrine, and squarely inside the founder's saga/event-driven experience.

Honest costs of the variant: operational-UI queries lose relational flexibility (provenance browsing and grant exploration require access-pattern-first single-table design and deliberate GSIs — design work Postgres let A1 skip); the deny hot channel to connected enforcement points needs push-without-servers (MVP answer: one-second long-poll on the cursor endpoint, which meets the ≤1s SLO by construction, with a streams-based push later); and if a hosted-evaluation tier is ever offered, the 100-item transactional read cap turns the cardinality doctrine from an optimization into a hard limit on slice size. Recommendation: **A1.1 is the preferred control-plane deployment**; A1's containerized/RDS shape remains documented as the second cloud's reference for the two-cloud cost model Report 2 requires.

## Running the gates

**Latency gate** (in-process single-digit ms p99; proxy hop low tens). Measured, not argued. The spike compiled the brief's scenarios to Cedar 2.4.2 (pinned to the container's rustc 1.75; production would use current 4.x on a current toolchain) and benchmarked on this session's shared container CPU. Correctness: all seven checks pass — subtree role allow and its outside-subtree denial, the sharing grant, the owner rule, the user-boundary opacity (a peer in the same org unit correctly *cannot* read another user's anchored note), deny-overrides-permit, and delegation-chain intersection. Latency, evaluation only over a prebuilt 14-entity slice, 200k iterations: **p50 5.9µs, p99 14.5µs, p99.9 47.7µs**. Pessimistic path — rebuilding the entire entity slice from JSON on every single request, no caching — **p50 231µs, p99 396µs**. Even the pessimistic path sits ~25x inside the gate; the realistic path (slice from a local Postgres read, ~0.1–1ms, plus microsecond evaluation) fits with an order of magnitude to spare. Caveats owned honestly: container-grade hardware, an old Cedar version, and a slice far smaller than the reference Organization — the production spike must re-run at thousands of principals and tens of thousands of grant edges, where slice *selection* (not evaluation) is the predicted cost center. **Verdict: PASS, provisional on the scale re-run.**

**Footprint gate** (free tier adds no external services). Passed by construction: the middleware is a crate, its state lives in the database the application already runs, and SQLite is the documented fallback for apps without one. **PASS.**

**Consistency gates.** Single-revision evaluation via MVCC snapshot reads: PASS by mechanism. Gap-free sequence: PASS on single-Postgres with a stated ceiling (wary list). Revocation ≤1s while connected: PASS trivially in the MVP topology; **UNPROVEN for the distributed proxy phase** — the design's largest deferred obligation, stated as such. Replayable idempotent log: PASS by mechanism (append-only table + cursor).

**Unit-economics gate** (marginal cost ≤ ⅓ of tier price; capped tier servable within cap). Computed on an AWS reference deployment. Fixed platform baseline: **$130/month lean** (small DB, small containers, load balancer, egress mitigation, storage, observability, domain) to **$380/month comfortable** (staging, tooling, paid webhook headroom, buffer). Marginal cost per entry-tier Organization ($30 cap; ~3 tenants, ~1M logged decisions/month, 30-day retention): **≈ $1.02/month — 97% margin**, passing the ≤$10 gate with 10x headroom. Marginal cost per B2B Organization ($500 tier; 50 tenants, ~50M logged decisions/month, 90-day retention): **≈ $42/month — 92% margin**, passing the ≤$167 gate 4x over. The decisive observation inside these numbers: log volume, not authorization itself, is the entire marginal cost, and **retention is the cost knob** — 30/90/365-day retention on the B2B profile moves storage from under a dollar to under ten, which is why retention belongs in tier quotas, exactly as the pricing lesson prescribed. **PASS.**

**Scale floor and ceiling.** Measured floor: the spike's toy scale. Projected comfortable ceiling for A1's single-Postgres store: Organizations into the low hundreds of thousands of grant edges and low thousands of writes/minute, bounded by the per-Organization sequence serialization; beyond that, the trait's Zanzibar backend is the designed relief valve. Stated, as the gate requires; unverified, as honesty requires.

## Feasibility Report

**Verdict: feasible, with two proof obligations and one deferred hard problem.** The MVP scope — core model, compiler, engine wrapper, Postgres store, both logs, cursor endpoint, Tower middleware with observe mode, RLS templates — is estimated at **10–14 weeks of part-time, agent-assisted development (~150–200 focused hours)** given the founder's existing Rust/AWS fluency and the fact that the two riskiest components were partially de-risked in this very session. Nothing in the design requires inventing new computer science; everything hard is either bought (evaluation engine, webhook delivery), inherited (MVCC for revision semantics), or explicitly deferred (distributed proxy consistency).

**Wins.** The spike is the headline: the brief's entire model — spine, grants, boundary, deny, delegation — compiles to a commodity engine and evaluates at microsecond speed, which converts the design's central bet from hope to measurement. The Postgres-as-substrate decision collapses three brief contracts (single-revision evaluation, gap-free sequencing, footprint) into properties of one boring, well-understood system. The margins are almost embarrassing — 97% and 92% — meaning pricing power lives entirely in product value, never in cost pressure, and the capped tier is genuinely safe to cap. And the design dogfoods every promise the documents make: exit hatch (customer's own database, portable policy language, replaceable delivery vendor), technology neutrality (everything sits behind the brief's contracts and the store trait), and buy-vs-own discipline (truth owned, transport bought).

**Shortcomings.** The distributed deny channel and cache invalidation for a proxy *fleet* is real engineering the MVP legitimately dodges and the proxy phase cannot; A1 asserts a solution shape (log fan-out over listen/notify or a stream) but has not designed it. Slice selection at reference-Organization scale is unmeasured — the microseconds above are evaluation, and the design's performance story rests on the cardinality doctrine keeping slices small, which is argued, not yet demonstrated. The query-plan API for arbitrary list filtering remains roadmap; until then the RLS templates carry that weight, which couples the data-plane story to PostgreSQL-family databases in practice. Cedar 4.x API migration from the spiked 2.4 is minor but real. There is no UI, no multi-region, no SOC 2 — all correctly absent from an MVP and all present in any funded competitor's pitch. And the entire hosted-tier cost model has a single-cloud basis; the two-cloud model Report 2 requires is still owed.

**Cost study and break-even.** Development: ~150–200 hours part-time across ~3 months; cash cost near zero (homelab, free tiers). Hosted platform, once launched: on the preferred A1.1 serverless control plane, **$17–117/month fixed, ~$0.22 marginal per entry Organization (99% margin), ~$33 per B2B Organization (93%)** — infrastructure break-even is **one customer of either tier**; on the A1 containerized shape (kept as the second-cloud reference), $130–380 fixed, ~$1 and ~$42 marginal, break-even 5–14 entry customers or one B2B. The honest second line: valuing founder maintenance time at a modest $2,000/month, sustainability break-even is **~5 B2B customers, or one B2B plus ~58 entry-tier, or ~74 entry-tier alone** — the number that says the business runs on the B2B tier while the entry tier funnels, exactly as the brief's pricing section intended. Sensitivity: the model is insensitive to authorization volume (evaluation is customer-side or microseconds) and sensitive only to log retention and webhook volume, both of which are quota knobs already in the tiers.

**Things to be wary of.** *The sequence bottleneck*: per-Organization gap-free counters serialize that Organization's writes; fine for spine/grant mutation rates, dangerous if anyone routes high-frequency events through it — the ceiling must be documented and monitored from day one. *Shared-database blast radius*: living in the customer's Postgres means ForgeGuard's queries compete with the app's; the reference deployment needs connection-pool discipline and the docs need a "dedicated schema, capped pool" prescription. *Slice-selection drift*: the doctrine keeps slices small only if promotion stays exceptional; a customer who promotes everything (misclassified resource types) degrades toward per-row checks — the misclassification signal from the data-plane section should become an actual metric with an alert. *Cedar stewardship*: AWS governs the language's roadmap; the trait boundary is the hedge, and the compiler should avoid Cedar-only expressiveness where the model doesn't demand it. *The deferred proxy problem*: do not sell the proxy body before the distributed consistency design exists; the middleware tier is honest today, the proxy tier is a promise. *Serverless query rigidity*: A1.1's DynamoDB single-table design must be validated against the operational UI's real query needs before the UI phase — retrofitting GSIs under load is the classic failure; sketch the access patterns now. *Benchmark humility*: every number above is container-grade or modeled; the fitness criteria demand target-hardware measurements before any number appears in marketing. *And the oldest warning in these documents*: none of this fails technically — the risks that kill it are the teardown's (invisibility) and the founder's calendar, and no architecture gate measures those.
