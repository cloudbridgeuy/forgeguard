# ForgeGuard — Report 2 (v2.0): Build On Top, or Compete? — Re-studied under Brief v1.4, with the Cloud Providers

*Version 2.1 — July 2026. Supersedes v1.1; v2.1 adds partial-plane services.*
*Status note: this is an implementation-options analysis, subordinate to the brief. The brief is deliberately technology-neutral; nothing evaluated here is part of the specification. This report is an input to engineering design, and competing designs answering these questions differently remain fully conformant to the brief.*
*What changed since v1.1: the brief acquired architecture fitness criteria, a synchronization contract, a full consistency model, native delegation chains, shadow mode, and the cardinality doctrine — turning what were preferences in the first analysis into pass/fail gates. This version re-runs the evaluation through those gates and extends it to what AWS, GCP, and OCI offer.*

## The question, re-posed through the fitness criteria

Version 1.1 of this report evaluated foundations by judgment. Version 1.4 of the brief makes judgment mostly unnecessary, because it supplies gates. The ones that decide foundation questions:

The **free-tier footprint gate**: the self-hosted middleware body must require no mandatory external services beyond what the application already runs. The **latency gate**: in-process decisions at single-digit milliseconds p99; the proxy hop in low tens. The **consistency gates**: single-revision evaluation per decision, revision tokens as public API, revocation-by-deny at or under one second while connected. The **synchronization gate**: a gap-free, replayable, per-Organization event log. The **unit-economics gate**: cost-to-serve within the tier margins. And the model obligations that any foundation must be able to *express*: the spine with the user-boundary rule, intersection semantics for delegation chains, and hypothetical evaluation for shadow mode and "view as."

Run every candidate through those gates and the field sorts itself into four classes. The brief's technology neutrality means this report evaluates the *classes*, naming specific products as instances a design might pick, never as requirements.

## Class A — Embeddable evaluation libraries: the only class that passes the footprint gate as a foundation

An evaluation engine consumed as a library — linked into the enforcement bodies, running in-process — passes the footprint gate by construction (it is not a service), passes the latency gate by construction (no network hop), and leaves every ForgeGuard-owned obligation (revision semantics, event log, spine constraints, delegation intersection, FGRN identity) exactly where the brief puts them: in ForgeGuard's compiler and stores. The leading instance remains the open-source Cedar library — Apache 2.0, mature, formally analyzed, with deny-overrides-permit semantics matching the brief's evaluation order and an entity-parent DAG that maps naturally onto spine-plus-grants — but the class also contains embeddable policy-engine runtimes of other lineages (WASM-compiled general-purpose engines, Rego reimplementations as libraries) and the purpose-built evaluator. Which instance wins is precisely the kind of question the brief now delegates to competing engineering designs, and the falsification spike from v1.1 generalizes accordingly: each candidate design compiles the brief's three killer scenarios (endpoint gating with M2M scopes, subtree roles with the user-boundary rule, "view as" as self-delegation) to its chosen engine and benchmarks against the fitness numbers with realistic entity slices built from one consistent grant-store read.

Two obligations this class leaves entirely unpaid, stated so no design forgets: entity slicing (deciding which nodes and edges to load per decision — where the cardinality doctrine keeps slices small, but a design must prove it), and the delegation-chain intersection, which no off-the-shelf engine expresses natively as a principal kind; every design implements chains in the compiler or evaluation wrapper, whatever the engine.

## Class B — Self-hostable service engines: optional backends, hard-blocked as foundations

The Zanzibar-lineage engines (SpiceDB, OpenFGA, and kin) fail the footprint gate as foundations: they are services with their own datastores, and mandatory-sidecar-plus-database is exactly what the free tier forbids. That verdict is now structural rather than preferential. But the consistency gates *raise* this class's value as an optional scale backend, and one instance stands out: SpiceDB's ZedToken model — per-request consistency selection, at-least-as-fresh semantics, snapshot reads — is the closest existing implementation of the brief's revision-token contract, and its Watch API is prior art for half the synchronization contract. A design that keeps the grant store behind a trait, as v1.1 recommended, can now say precisely what the trait must express to make a Zanzibar backend slot in later: snapshot-at-revision reads (for single-revision evaluation), revision-returning writes (for public tokens), and a change stream (feeding the event log). Those three requirements belong in any engineering design's trait definition regardless of whether the backend is ever built.

## Class C — Hosted authorization platforms and managed engines: never foundations, occasionally enterprise checkboxes

Hosted platforms (Oso Cloud, Permit.io's cloud, the managed FGA offerings) fail three gates at once — footprint, exit hatch, and latency (a network hop per decision competes with the in-process budget) — and remain rejected as foundations for the same structural reasons as v1.1, now with the added observation that their per-MAU and per-check meters cannot be reconciled with the unit-economics gate at the capped tier. Their one legitimate role is unchanged: optional evaluation or storage backends behind the same trait, for enterprises already committed to one.

## The cloud providers

### AWS: a commoditized engine service, and the escape hatch built into its own language

Amazon Verified Permissions is the most consequential cloud offering for this analysis, for a reason that postdates ForgeGuard's original AVP experience: in mid-2025 AWS cut single-authorization pricing by up to 97%, to $5 per million requests. Practitioner math that once read $8,250/month for 70M monthly checks now reads roughly $350, and AWS showcases customers batching and caching their way to hundreds of millions of checks monthly at tolerable cost. Two consequences. First, the *market signal*: AWS just commoditized per-decision pricing for managed authorization — which validates the brief's refusal to meter decisions (competing on a meter the hyperscaler prices at $5/million is a losing game) and confirms tenant-metering as the differentiated axis. Second, the *evaluation*: even at the new price, AVP fails the footprint gate (hosted), fails the latency gate (a network hop per decision, with no built-in cache — practitioners build their own caching layers, which reintroduces the New Enemy windows the brief's consistency model exists to bound), and offers neither revision semantics, nor a grants store (entities are passed per request — entity slicing remains the caller's job), nor an event log. Practitioner complaints center on developer experience, versioning, and cross-region replication — the exact layers ForgeGuard owns.

What makes AWS unique among the clouds: its managed service speaks an open, embeddable language. A design that chooses a Cedar-class library gets, for free, the only cloud-compatible story in the category — self-hosted in-process evaluation as the foundation, with AVP available as an *optional* managed policy-store backend for AWS-committed enterprises, policies portable in both directions. Cognito slots in exactly where the brief puts all authentication: a federation target, commodity plumbing. The rest of AWS (queues, streams, object storage, serverless) is substrate for the *hosted control plane* — an infrastructure decision for the paid tiers, orthogonal to the foundation question and untouched by the footprint gate, which governs the customer's self-hosted body, not ForgeGuard's own cloud.

### GCP: the strongest validation of the form factor, and the loudest silence in the market

Google sells no application-level fine-grained authorization service. The company that invented Zanzibar, published the paper, and runs Drive, Docs, and Cloud IAM on it offers customers no way to rent it — the entire Zanzibar-engine ecosystem exists because Google left the paper on the table and walked away. For the teardown's discoverability thesis and the brief's whitespace claim, this is the loudest gap evidence available: the model's inventor validated the architecture at planetary scale and declined to productize it for customer applications.

What GCP does sell is the Identity-Aware Proxy, and it deserves careful attention as *prior art for ForgeGuard's proxy body*: IAP sits in front of applications, authenticates every request, authorizes centrally, and passes verified identity downstream in a cryptographically signed JWT header that backends validate — architecturally, the header contract, shipped at Google scale since 2017. It equally marks the boundary ForgeGuard crosses and IAP does not: IAP's authorization is coarse (role- and group-based access to *applications*, with context conditions), bound to Google identities and GCP load balancers, with no tenancy spine, no resource-level policy, no entitlements, no grants graph, and no story for the customer's own multi-tenant product semantics. IAP answers "may this employee reach this internal app"; ForgeGuard answers "may this principal do this action on this resource in this tenant subtree." A design cannot build on IAP — it is not extensible in ForgeGuard's dimensions — but any design document should cite it: the signed-header enforcement pattern is not novel, it is proven, and ForgeGuard's novelty is what flows *through* the headers. GCP's Identity Platform, like Cognito, is a federation target; GCP infrastructure is hosted-control-plane substrate.

### OCI: spine prior art, and a vendor whose own guidance is to hand-roll

Oracle offers no application-level authorization service either. Its two relevant assets are instructive in opposite directions. OCI compartments are a nested hierarchy where policies written at any level apply to everything downstream — the tenancy-spine pattern with policy inheritance, deployed as the *organizing principle of an entire cloud*, which makes it excellent prior art for the brief's core model (worth citing alongside the WorkOS single-parent validation). But compartments govern OCI's own resources, not a customer application's. And when Oracle publishes reference architecture for fine-grained access control in customer-facing applications, the guidance is: put an API gateway in front, write a *custom authorizer function*, validate tokens against the identity domain, and implement the authorization logic yourself. The vendor's official answer to ForgeGuard's problem is "hand-roll it at the gateway" — which is simultaneously gap evidence for the brief and a description of the precarious pattern the founding startup lived. OCI IAM Identity Domains is, once more, a federation target; OCI infrastructure, substrate.

### The cross-cloud summary

No cloud provider offers a foundation. All three offer the same two things — an authentication federation target and control-plane hosting substrate — plus one distinctive asset each: AWS, an optional managed backend reachable through an open embeddable language; GCP, form-factor validation and the market's loudest whitespace evidence; OCI, spine prior art and hand-roll-it guidance that reads like the brief's problem statement. And a strategic risk worth stating candidly: the clouds are one product decision away from this market. AWS assembled Cedar, AVP, Cognito, and API Gateway without composing them into a multi-tenant product; the day a hyperscaler ships the composition, it ships with unbeatable distribution. ForgeGuard's defenses are the ones the brief already chose — the model (spine, boundaries, FGRNs, delegation chains), the sovereignty story no hyperscaler will tell, and speed — plus one this analysis adds: cloud-optionality, since a product whose evaluation runs in-process and whose backends are traits is the only shape that works identically on all three clouds and on a garage server, which no cloud-native competitor can claim.

## Class E — Services that implement parts of the design

Beyond foundations, a design may buy *planes*: delivery, provisioning, billing, storage. The decisive observation: the fitness gates bind the **customer's runtime** — the hot path and the self-hosted body — not ForgeGuard's own hosted control plane, which is ordinary SaaS infrastructure where a small team's calculus favors buying operations. Three tests sort every candidate. The *gate test*: anything in the customer's decision path or self-hosted body can only ever be optional. The *truth test*: no service may become the source of truth for the spine, grants, snapshots, or the event sequence — the three append-only truths are the product. The *differentiator test*: the entitlements/permissions convergence and the model are never outsourced.

Applied per plane. **Webhook delivery** is the strongest buy: the synchronization contract made the log the primitive and push a mode, so delivery is transport, not truth — precisely what a mature webhook-as-a-service category sells (MIT-licensed self-hostable servers with compatible hosted SaaS exist, alongside cheaper and fully-open alternatives, at roughly order-of-magnitude price spreads). Two obligations survive any vendor: the gap-free per-Organization sequence and Organization-key signing live in payloads, vendor-independent; and per-message pricing must be modeled against the capped tier's unit-economics gate. One finding transcends buy-vs-build: the **Standard Webhooks specification** — authored by Svix, Twilio, Kong, Supabase, Mux, ngrok, and Lob, adopted by OpenAI, Anthropic, and Google — is the industry's shared convention for webhook signing and delivery, and the synchronization contract should conform to it; conforming to an open specification is fully compatible with the brief's technology neutrality, and it means consumers verify ForgeGuard events with tooling they already run. **Entitlements and feature-flag SaaS** fail the differentiator test absolutely: wrapping one as the operational plane rebuilds the four-drifting-systems disease inside the cure; the only legitimate relationship is migration importers from them. **Authentication, SCIM provisioning, and billing** are bought freely — authN was federated by the brief from day one, provisioning services are adapters feeding the idempotent upsert API, and tenant-metering is low-cardinality enough that a plain payment processor suffices for years. **Decision-log storage** splits along the truth test: managed storage substrate yes; an audit-log SaaS *as* the log no, since replay against snapshot-plus-revision is schema-owned forensics — export to customers' audit tooling is a feature, never a dependency. **Managed grants stores** remain Class B/C behind the trait.

One governing principle: ForgeGuard holds itself to the exit hatch it sells. Its own control plane prefers open-core or replaceable services — a delivery layer it could self-host, storage it could migrate — so the sovereignty pitch is dogfooded rather than merely marketed. And one honest note in the other direction: buying operations is not a compromise for a small team, it is how a hosted tier ships at all; the discipline is in *what* is bought (delivery, storage, billing) versus what never is (truth, model, convergence).

## The recommendation, restated through the gates

The layered strategy of v1.1 survives re-study and comes out stronger, because it is now *derived* rather than argued: the footprint, latency, and exit-hatch gates admit only Class A (embeddable libraries) as a foundation; the consistency gates define the trait contract that keeps Class B (Zanzibar engines) available as scale backends — snapshot-at-revision reads, revision-returning writes, a change stream; Class C and the cloud services are optional enterprise backends behind the same trait, never load-bearing; and everything the gates don't outsource — the compiler, the spine and its constraints, FGRN identity, the event log, delegation intersection, hypothetical evaluation, the enforcement bodies, provenance — is ForgeGuard, in any design, with any engine. Competition happens at the product layer, standing where useful on engine commons; the clouds are federation targets underneath, substrate behind, and validation all around.

Open items for the first engineering design, updated: evaluation of Standard Webhooks conformance for the synchronization contract's push mode; the compile-and-benchmark spike per candidate engine against the fitness numbers (three killer scenarios, single-revision entity slices); the trait definition carrying the three backend requirements above; and one new falsification the cloud research adds — a cost model of the hosted control plane on at least two clouds, because the unit-economics gate binds ForgeGuard's own serving costs, and cloud-optionality is only real if it is priced.
